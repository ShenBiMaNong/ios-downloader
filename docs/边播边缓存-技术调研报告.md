# 视频「边播边缓存」技术调研报告

> 调研时间：2026-11 ｜ 范围：本仓库（Flutter，iOS 为主）内置浏览器嗅探 → 下载 → 播放全链路
> 目标：**播放正在下载的视频，且播放的字节与下载落盘的字节是同一份（真实缓存），下载完成即得完整产物，绝不重复下载。**
> 结论均附出处与核验状态（「官方文档原文」「社区实践」「未能核验」）；本仓库代码证据附文件:行号。

---

## 1. 结论速览（TL;DR）

1. **「file:// 直接播正在 append 的 .part」不可行**：iOS AVPlayer / Android ExoPlayer 读到当前 EOF 就当作播完/流结束，都不会等待文件增长（iOS: SO 11294990；Android: androidx/media#320 官方维护者明确"不支持动态变更输入长度"）。
2. **mp4 直链的正解 = 本地 HTTP 代理服务器**：把播放器请求接到一个本地 HTTP 服务上，下载器继续顺序写缓存文件，代理按 Range 从缓存文件读已下载区间喂播放器；未下载到的区间**阻塞等待或直接回源取回写盘**。播放的字节 == 落盘的字节 == 最终产物，天然零重复下载。
   - 现成库：**`http_cache_stream` 0.3.2**（pub.dev，为 video_player 场景定制，与本项目 dio+video_player 完全对口）；iOS 原生同路线：KTVHTTPCache（唱吧 2516★）、SJMediaCacheServer（306★）。
3. **HLS 有官方更优解**：`AVAssetDownloadTask` 是 HLS-only（mp4 直链不可用，官方文档语境核实）；但官方现代文档明确——**下载进行中想播放，复用当初的同一个 `AVURLAsset` 建 AVPlayerItem 即可，播放器会直接读已缓存的分段**（"reads locally cached segments during concurrent playback"）。对本项目现有 HlsBridge 只需新增一个 `playWhileDownloading` 桥接方法。
4. **不推荐的两条路**：ExoPlayer 自定义 DataSource 等文件增长（官方确认硬伤：时长/SeekMap 无法动态更新）；media3 SimpleCache（缓存是私有分块布局，不能当最终 mp4 产物，且 video_player 无注入入口）。
5. **硬性前提（两平台一致）**：mp4 需 **faststart（moov 前置）** 才可能在下载中解析起播；非 faststart 的部分文件不可解析（SO 47568075）。`http_cache_stream` 的 `rangeRequestSplitThreshold` 可缓解：播放器发尾部探测（取 moov）时直接回源取回写盘，每字节仍只取一次。

## 2. 需求定义（判定标准）

| 判定项 | 标准 |
|---|---|
| 真实缓存 | 播放器读到的字节 == 下载器写盘的字节（单一数据流，无第二条拉取通道） |
| 避免重复下载 | 一次播放过程结束后，磁盘上就是完整最终 mp4；播放 ≠ 额外下载一份 |
| 起播体验 | 点「播放」→ 立即起播（无需等全量下载），可暂停/恢复、可显示下载进度 |
| 兼容性 | 不破坏现有「纯下载」链路与资源库 |


## 4. 候选路线调研

### 4.1 路线 A：本地 HTTP 代理服务器（mp4 直链 · 推荐）

**原理**：App 内起一个 `dart:io` HTTP 服务器（`http://127.0.0.1:<port>/...`）。播放器（`video_player.networkUrl`）向本地服务器发请求；下载器把源站字节顺序写进**同一个缓存文件**；服务器收到播放器的 Range 请求时从缓存文件读**已下载区间**返回，未下载区间要么**阻塞等待下载推进**（CachingPlayerItem 模式），要么**另开直连回源取回该段写盘**（split download）。

- 字节唯一性：播放器读的 = 下载器写的 = 缓存文件；下载完成时缓存文件**改名就位 = 最终 mp4**（`CompleteCacheState` 语义），零二次下载。
- iOS 侧可行性依据：AVPlayer 依赖 Range（不支持 Range 的服务器直接失败，flutter/flutter#56665）；本地 HTTP + Range 是 iOS 渐进式播放社区主流（KTVHTTPCache、SJMediaCacheServer、better_player 的 iOS 缓存实现 = CachingPlayerItem 自定义资源加载，betterplayer#714）。
- Android 侧可行性依据：ExoPlayer 以 HTTP+Range 播放本地服务器 URL 没有动态长度问题（长度固定 = 源文件总长，由代理从源站响应头拿到）。

**现成库核验（pub.dev 官方 README/changelog 原文）**：
- **`http_cache_stream` 0.3.2**（MIT，verified publisher，3 天前发布，24 likes / 2.66k 下载）：本地 HTTP 服务器代理、边下边播、Range 请求支持、断点续传（重启后可继续）、自定义请求/响应头、`cacheFileResolver`（自定义缓存文件路径）、`cacheStateStream`（进度）、`rangeRequestSplitThreshold`（远距 Range 直接回源）、`ensureActive()`（iOS 后台恢复后重建监听 socket）。README 示例即 `VideoPlayerController.networkUrl(cacheUrl)`。
  - [pub.dev 包页](https://pub.dev/packages/http_cache_stream) ｜ [changelog](https://pub.dev/packages/http_cache_stream/changelog) ｜ [API 索引](https://pub.dev/documentation/http_cache_stream/latest/http_cache_stream/)
  - 成熟度风险：年轻包，0.2/0.3 版 changelog 在集中修「部分缓存损坏、续传偏移、删除/截断后错误续写」类 bug（changelog 0.2.1/0.3.0/0.3.2）——**"缓存文件=最终产物"的前提是字节正确，落地必须加完成后校验**（包提供 `validateCache()`/`resetCache()`）。
- **KTVHTTPCache**（唱吧，2516★，MIT，iOS 原生，"A powerful media cache framework"）：同一路线（本地代理喂 AVPlayer）。GitHub API 已核验仓库与描述；README 正文本次抓取失败，使用细节以仓库为准。
- **SJMediaCacheServer**（306★，MIT）：仓库描述明确支持 MP3/AAC/WAV/FLAC/OGG/MP4/MOV 文件型媒体 + HLS 代理缓存。README 正文本次抓取失败。
- **just_audio LockCachingAudioSource**（同源机制印证）：本地 HTTP 代理 + 顺序下载缓存，"caches the audio while it is being downloaded and played (experimental)"；`cacheFile` 可自定义缓存路径、`resolve()` 完成后直接返回缓存文件 source（=缓存文件即产物）。它是音频库，不能放视频，但机制与 http_cache_stream 同源（后者 Credits 声明 "began as a custom implementation of just_audio's LockCachingAudioSource"）。

### 4.2 路线 B：AVAssetResourceLoaderDelegate 自定义 scheme（iOS 专用 · 备选）

**原理**：`AVURLAsset` 换成自定义 scheme URL（如 `vdl://...`），用 `AVAssetResourceLoaderDelegate` 接管 AVPlayer 的所有加载请求：`shouldWaitForLoadingOfRequestedResource` 返回 true = 你接管，数据未到**不调用 finishLoading** → AVPlayer 停在 buffering 等待；下载线程继续写 .part，loader 从 .part 分段读已下载区间 `respondWithData`，未覆盖区间保持 request pending。（官方文档原文：[shouldWaitForLoadingOfRequestedResource](https://developer.apple.com/documentation/avfoundation/avassetresourceloaderdelegate/resourceloader(_:shouldwaitforloadingofrequestedresource:))）

**坑（均有出处）**：
- 必须自定义 scheme；http/file 不触发 delegate；HLS ts 段不走 delegate（SO 18205588、29434682）。
- `contentInformationRequest` 必须填对 contentType/contentLength/isByteRangeAccessSupported，否则 AVPlayer 只请求前 2 字节就不再继续（SO 24746453）。
- **faststart 硬性前提**：moov 在尾部的非 faststart mp4，部分下载时首帧都解析不了（SO 47568075）。
- Content-Length 必须下载前拿到（HEAD/响应头）；未知长度报 -11849（SO 45786283）。
- 线程：请求在 `setDelegate(_:queue:)` 指定 queue 上同步处理；异步加载返回前对 loadingRequest 保持强引用（官方文档）；不要在 delegate queue 上做网络 IO。
- 开源参照：everappz/AVAssetResourceLoader（240★）、renjithn/AVAssetResourceLoader-Video-Example（30★）、CachingPlayerItem 模板（SO 45786283）。

**工作量**：Swift 桥接约 200-400 行（参照现有 HlsBridge 规模）；video_player 的 source 从 file:// 换自定义 scheme URL。
**对比路线 A**：A 是通用方案（双端 + 任意播放器 + 进度/续传现成），B 只解决 iOS 且要自研加载协议细节；**除非不想引入新依赖，否则选 A**。

### 4.3 路线 C：ExoPlayer 自定义 DataSource 等文件增长（Android · 放弃）

- 官方维护者 icbaker 明确答复「ExoPlayer 不支持动态变更输入长度，支持需要重大架构改动」，issue 已关闭（[androidx/media#320](https://github.com/androidx/media/issues/320)）。
- 社区自定义 DataSource（open() 返回 `C.LENGTH_UNSET` / read() 定期重开文件）顺序播放可行，但**时长/SeekMap 由初始长度推导，文件变长后无法动态更新**，seek 超过初始时长会失败或跳回起点（#320 内实现 + #7727/#6411 先例）。
- video_player 2.x 不暴露 DataSource 注入点（pub.dev README 仅 networkUrl/file/asset；flutter/flutter#171208 无法透传自定义播放选项）。
- 结论：不推荐；本地 HTTP 代理（路线 A）在 Android 同样成立且无此问题。

### 4.4 路线 D：media3 SimpleCache / CacheDataSource（Android · 不满足诉求）

- CacheDataSource 设计目的 = 边播边把读过的字节写盘 SimpleCache 供离线二次观看；但缓存是**分块（CacheSpan）+ 元数据的私有布局，不是可直接当 .mp4 复用的原始文件**，官方无「缓存文件即产物」承诺（官方缓存指南页 developer.android.com 本次被网络拦截，未能核验原文）。
- video_player 2.x 无注入入口；要用需自写原生层。
- 结论：满足"免二次下载缓存播放"但不满足本项目"缓存文件=最终 mp4"的判定标准，不采用。

### 4.5 业界做法与真实世界源（faststart 线）

**浏览器渐进式播放（伪流式）**：MDN 官方文档原文确认「byte-range requests 开启时，媒体可 seek 到尚未 buffered 的部分」——即 faststart mp4 + Range 是浏览器边下边播的机制基础。来源：[MDN buffering/seeking/time ranges](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Audio_and_video_delivery/buffering_seeking_time_ranges)（官方文档原文）。

**桌面下载器**：IDM 官方 FAQ 与 features 页**均未找到「start downloading, then play / 边下边播」功能说明**（官方文档可核验为"无此功能文档"）；其 FAQ video6 解释了「IDM 只捕获到 1.99MB/1.69MB 部分视频」= 浏览器渐进式播放被部分捕获的现象（[官方 FAQ](https://www.internetdownloadmanager.com/register/new_faq/video6.html)，官方文档原文），侧面印证直链渐进式下载在桌面端即"播放驱动下载"。Video Download Helper / Via / Documents by Readdle：本次网络不可达或站点已改版，功能层面**未能核验**。

**B 站（社区项目文档，bilibili-API-collect 镜像）**：
- FLV 格式已下线（文档标注"应避免使用 fnval=0"）；
- 较高分辨率走 **DASH**，其 m4s 视频流 **initialization 字段 = ftyp box + moov box 在文件头部**，随后是 sidx 与 moof/mdat 分片 —— **即 fMP4 且 moov 在前，对"顺序下载边下边播"天然友好**；较低分辨率与老视频保留 MP4，`html5` 模式 MP4 无 Referer 鉴权可直接渐进式播放；MP4 durl 不分段；
- B 站 upos 源支持 Range/分段请求。
- 来源：[bilibili-API-collect（维护镜像）videostream_url.md](https://github.com/pskdje/bilibili-API-collect)（社区实践/项目文档）。

**YouTube / 抖音**：YouTube 伪流式可 seek 未下载部分（SO 3302384，2010-2013 较旧）；现行 DASH fMP4 与 progressive itag 的 moov 位置**未能核验**；抖音**未能核验**。

### 4.6 HLS 特论：官方「边下边播 + 读已缓存分段」（推荐改造现有 HlsBridge）

- **AVAssetDownloadTask 只支持 HLS**，不支持 mp4 直链（官方文档全程 HLS 语境，产物为私有 .movpkg；SO 40424263 印证）。
- **官方现代文档原文**：「To play an asset while its download is in progress, reuse the AVURLAsset you supplied to the AVAssetDownloadConfiguration. The asset reads **locally cached segments** during concurrent playback when the streaming variant matches the downloading variant.」（[AVAssetDownloadTask | Apple](https://developer.apple.com/documentation/avfoundation/avassetdownloadtask)）——即官方支持下载中播放，且播的是已缓存分段（不重复拉取）。
- 归档 Media Playback Guide「Playing Offline Assets」给出 `downloadAndPlayAsset` 完整示例：同一 AVURLAsset 同时建下载任务与 AVPlayerItem，并明言 "the playback engine streams the requested variant … in combination with the **pieces of the asset that are stored locally**"（[官方归档文档](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/MediaPlaybackGuide/Contents/Resources/en.lproj/HTTPLiveStreaming/HTTPLiveStreaming.html)）。
- 风险标注：该表述源自 2016–2018 归档文档，iOS 10 时代社区反馈此模式不稳定（"要么能播要么能下"，SO 45434092）；现代版本需真机实测。
- 对本仓库：现有 HlsBridge 持有原始 `AVURLAsset`（[AppDelegate.swift:86-97](D:\other\proj\downloader\ios\Runner\AppDelegate.swift#L86-L97)），**新增 `playWhileDownloading(taskId)` 桥接方法，用同一 AVURLAsset 建 AVPlayerItem 播放即可**，不引入任何新依赖；`playOffline`（下载完成后播本地 .movpkg）保留。

### 5.1 faststart 判定与探测（成本几乎为零）

- **判定原理**（官方文档原文）：moov 在文件尾部时播放器"has to download the entire file before starting playback"；moov 在前则服务器可直接开始发送内容（[nginx mp4 module | nginx](https://nginx.org/en/docs/http/ngx_http_mp4_module.html)）。FFmpeg `-movflags +faststart` 官方原文：第二遍扫描把 moov 搬到文件头，"will not work in various situations such as fragmented output"（[ffmpeg-formats | ffmpeg.org](https://ffmpeg.org/ffmpeg-formats.html)，官方文档原文）。
- **探测方法（纯代码）**：读文件头 1~4KB，按 box 链解析（`size + fourcc`）：`ftyp → (free/wide) → moov → mdat`，moov 出现在 mdat 前即 faststart；fMP4 则 moov/mvex 在前、moof+mdat 分片在后。现成工具：Bento4 `mp4dump`（[官方文档](https://www.bento4.com/documentation/mp4dump/)）、`qtfaststart --list`（[PyPI](https://pypi.org/project/qtfaststart/)，基于 FFmpeg qt-faststart.c，处理 mdat 在 moov 前的文件并支持 stco/co64 偏移修正）。
- **对"边播边缓存"的意义**：起播前先做 1 次头部小请求探测 moov 位置——faststart/fMP4 → 直接进"边播边缓存"通道；非 faststart → 走降级（§6）。
- **真实世界源**（社区项目文档）：B 站 DASH 的 m4s 视频流 `initialization` 字段 = 文件头部的 ftyp+moov（示例 0-821 字节），随后是 sidx 与 moof/mdat 分片——**fMP4 且 moov 在前，顺序下载即可边下边播**；`platform=html5` 的 MP4 无 Referer 鉴权、可渐进式播放（[bilibili-API-collect 镜像](https://github.com/pskdje/bilibili-API-collect)）。YouTube 现行 DASH fMP4 与 progressive itag 的 moov 位置、抖音：**未能核验**，需实测抓包。

### 第一步：mp4「边播边缓存」= `http_cache_stream` 独立服务

1. 新增 `lib/services/playback_cacher.dart`（封装 `HttpCacheManager`）：
   - `HttpCacheManager.init()`（启动时一次）；`config.requestHeaders` 配 Referer（取嗅探来源页）/UA（复用 [download_manager.dart:93-95](D:\other\proj\downloader\lib\services\download_manager.dart#L93-L95) 的 UA）。
   - **`cacheFileResolver` 把缓存文件直接指到 `Documents/Downloads/<title>.mp4`** → 下载完成即最终产物，零拷贝、零二次下载。
   - `getCacheUrl(source)` 拿本地 URL；`cacheStateStream` 接现有进度 UI（资源库下载中条目）。
2. `PlayerPage` 支持网络源：`PlayableItem` 增加可选 `url` 字段（`VideoPlayerController.networkUrl`），本地文件路径与缓存 URL 二选一；手势/播放列表逻辑不变。
3. 入口：资源库下载中任务加「边播边缓存」按钮；`video_marker.js` 操作卡可加"立即播放"（直链 mp4）。
4. 完成后校验：`validateCache()` + 与源站 Content-Length 比对；通过才写资源库元数据（复用 `DownloadManager.scanSaved` 的 JSON 形态），失败则 `resetCache()` 重来——**这是"缓存文件=产物"的底线校验**（包尚年轻，changelog 集中修过缓存损坏类 bug）。
5. 后台：包现有 `BackgroundTask`（尽力而为）；说明文案写"息屏后可能暂停缓存"。

### 第二步：HLS「边下边播」= HlsBridge 新增 `playWhileDownloading`

1. `AppDelegate.swift` HlsBridge 增加 method `playWhileDownloading(taskId)`：从 `taskIds[taskId]` 拿到原始 `AVURLAsset`，建 AVPlayerItem 用 `AVPlayerViewController` 播放（复用 [AppDelegate.swift:180-191](D:\other\proj\downloader\ios\Runner\AppDelegate.swift#L180-L191) 的展示逻辑）。
2. Dart 侧 `HlsManager` 暴露 `play(taskId, {bool whileDownloading})`；资源库 HLS 下载中任务加「边下边看」按钮（进度 < 1 时用 whileDownloading，完成走 playOffline）。
3. 真机验证 iOS 版本下「复用同一 AVURLAsset 读本地缓存分段」的稳定性（历史反馈 iOS 10 时代不稳）。

### 第三步（可选）：Android HLS

`http_cache_stream` 声称支持 HLS/DASH 动态 URL 模式（changelog 0.1.0），但 Android 侧 HLS 现有走 m3u8 分片 + ffmpeg 转换；「边下边播」可先不做，保持现状。

### 明确不做 / 维持降级

- ExoPlayer 自定义 DataSource 等文件增长：官方不支持，不做。
- SimpleCache 当产物：缓存布局私有，不做。
- 非 faststart mp4 的兜底：起播前先做 §5.1 的头部探测；不可播时降级提示"该视频需下载完成后播放"（沿用 [嗅探视频展现方式-体验调研报告.md:144](D:\other\proj\downloader\docs\嗅探视频展现方式-体验调研报告.md#L144) 的降级原则）。
  - 中期可选（源支持 Range 时）：**尾部 moov 预取 + 下载期重排**（双 pass）——需实现 box 解析 + stco/co64 偏移修正（moov 前置后所有 chunk 偏移 +moov 大小），等价于移植半个 qt-faststart；或 **ffmpeg 流式 remux 成 fMP4**（`-movflags frag_keyframe+empty_moov`，但破坏"最终文件与直链字节一致"的目标）。两者均未定案，先不做。
- 与页内原生播放的冲突处理：进入 App 播放器前先 `video.pause()` 暂停页内 `<video>`，返回时按需恢复（沿用既有 JS 通道，无新依赖）。

## 7. 风险与未能核验清单

1. **http_cache_stream 成熟度**：0.3.2（3 天前发布，2.66k 下载）；"缓存文件=最终产物"依赖其字节正确性，0.2/0.3 版 changelog 仍在集中修缓存损坏类 bug → 必须加完成后校验，并在真机/CI 上实测大文件（>500MB）与断点续传。
2. **AVPlayer 对非 faststart mp4 的行为**：split download（尾段回源取 moov）能否稳定起播，端到端未实测（未能核验）。
3. **HLS 复用 AVURLAsset 边下边播**：官方表述源自归档文档 + iOS 10 时代社区负面反馈，现代 iOS 版本稳定性未实测。
4. **iOS 本地代理在后台被系统回收 socket**：包内 `ensureActive()` 声称已处理（changelog 0.2.1/0.0.6），未实测。
5. **KTVHTTPCache / SJMediaCacheServer README 正文**本次抓取失败，未逐条核验其功能细节（GitHub API 核验了仓库与描述）。
6. **media3 SimpleCache 官方缓存指南页**（developer.android.com）被网络拦截，未能核验原文。
7. **商业 App（IDM iOS、Documents by Readdle、nPlayer）内部实现**：闭源，未能核验；IDM 官方文档可核验为**无「边下边播」功能说明**（[官方 FAQ video5](https://www.internetdownloadmanager.com/register/new_faq/video5.html) / [features](https://www.internetdownloadmanager.com/features2.html)），其 FAQ video6 印证桌面端"播放驱动下载"的渐进式捕获现象。
8. **YouTube 现行 DASH fMP4 与 progressive itag 的 moov 位置**、**抖音**：未能核验（需实测抓包）。
9. **非 faststart 变通成本**（尾部 moov 预取重排 / remux）的具体工作量数字：分析性结论，无权威来源，未能核验。
10. **Video Download Helper / Via / Documents by Readdle 功能层**：官方站不可达或改版，未能核验。
